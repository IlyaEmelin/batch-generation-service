# Plan.md — проект спринта 1: пакетная генерация карточек товаров

> **Назначение документа:** рабочий план спринта. Часть решений уже согласована и помечена как принятая, остальное остаётся гипотезами до проверки экспериментами.

## 1. Цель и критерии успеха

Собрать сервис, который из входных данных товара генерирует карточку для маркетплейса, обработать пакет из `benchmark.jsonl`, измерить качество, производительность и стоимость, затем обоснованно выбрать между собственной ВМ и внешним API.

Обязательные ограничения из задания:

- **Формат:** не менее 80% карточек проходят автоматическую структурную валидацию.
- **Время:** 300 карточек обрабатываются не дольше 8 минут на одной T4.
- **Стоимость:** выбранный вариант стоит не более 25 ₽ за 1000 карточек при плановом объёме 50 000 карточек в месяц.
- **Входной контекст:** не более 1500 токенов на товар, считая токенайзером модели.
- **Воспроизводимость:** числа итогового отчёта должны подтверждаться сохранёнными результатами прогонов.

Валидность в рамках задания — прежде всего соответствие формату, а не смысловая достоверность или качество маркетингового текста. Эти аспекты не смешиваем в одной метрике.

### 1.1 Операционные допущения, согласованные до реализации

- **Среда замеров — локальная GPU ноутбука, не T4.** Доступа к T4 на момент спринта нет, поэтому прямые замеры выполняем только на текущей видеокарте ноутбука и указываем её в отчёте вместе с версиями драйвера, CUDA, PyTorch и vLLM. В итоговом отчёте явно пишем, что доступа к T4 нет; все выводы о скорости и стоимости сделаны по локальной GPU. Соответствие SLA на T4 не выдаём за измеренный факт: при необходимости показываем только как оценку/ограничение задания.
- **Формат пачки — один запуск целиком.** `benchmark.jsonl` обрабатываем как единый пакет: 300 товаров на входе, ровно 300 строк в `outputs/predictions.jsonl`, порядок строк совпадает с порядком входа. Результаты по частям не считаем сдаваемым артефактом.
- **API-сравнение — только OpenRouter, один фиксированный платный эндпоинт.** Берём instruct-модель, указанную в задании, `openai/gpt-oss-20b` (без суффикса `:free`), через `https://openrouter.ai/api/v1` и ключ `OPENROUTER_API_KEY`. Прямой OpenAI (`OPENAI_API_KEY`, `https://api.openai.com/v1`) не проверяем и автоматический выбор провайдера не добавляем. Для стоимости используем только реальный `usage` из ответа OpenRouter. Модель, base URL и дату прогона сохраняем в `outputs/report.json` (`api_comparison.model`, `api_comparison.base_url`, `api_comparison.api_run_date`), чтобы результат можно было проверить позже, когда каталог моделей изменится.
- **Один источник чисел.** Все цифры README берутся из `outputs/report.json`, а отчёт считается из сохранённых результатов прогона. Ручные числа в README не допускаются: при расхождении приоритет у отчёта.

### 1.2 Что из ограничений следует арифметически

Проверяем формулы до прогонов, чтобы понимать запас:

- Ограничение по цене при тарифе 65 ₽/час: `25 ₽ за 1000 карточек` соответствует `25 * 3600 / 65 ≈ 1385` секунд оплаченного времени на 1000 карточек, то есть **≈ 415 секунд (6.9 минуты) на 300 карточек** и throughput **≥ 0.72 карточки/с**. Это строже ограничения по времени (8 минут ≈ 0.625 карточки/с), поэтому целевой показатель берём по цене, а не по времени.
- Для API при ориентировочных 1500 входных и 350 выходных токенах на карточку получаем `(1500 * 20 + 350 * 60) / 1_000_000 ≈ 0.051 ₽`, то есть ≈ 51 ₽ за 1000 карточек. После прогона оценку заменяем фактическими `usage` из ответов OpenRouter. Если API-прогон не дошёл до модели или OpenRouter не вернул `usage`, стоимость API не равна нулю: в машинном отчёте ставим `costs.api = null`, а причину недоступности оставляем в `api_comparison`.
- Отсюда ориентир для Этапа 7: свой сервер выгоден, пока оплаченное время партии (включая старт и загрузку модели) дешевле, чем `0.051 ₽ × N` для API. Переход зависит от накладных расходов на запуск, поэтому время старта измеряем, а не предполагаем.

## 2. Что известно и чего пока не утверждаем

### Известно из материалов

- Локальная модель: `Qwen/Qwen2.5-1.5B-Instruct`, сервер инференса — vLLM.
- Датасеты: `dev.jsonl` (40 товаров) для разработки и настройки; `benchmark.jsonl` (300 товаров) для итогового замера. Оба файла уже лежат в рабочей папке, профиль снят на Этапе 1.
- Структура карточки: `product_id`, `description`, `pros`, `cons`, `tags` с ограничениями из задания.
- Для длинных товаров нужно ограничить вход до 1500 токенов.
- Нужно сравнить варианты параметров генерации, уровни `concurrency` и внешний API через OpenRouter.
- Тарифы для расчёта: ВМ с T4 — 65 ₽/час; API — 20 ₽ за 1 млн входных токенов и 60 ₽ за 1 млн выходных токенов.
- Ожидаемые артефакты сдачи: `README.md`, `run_batch.py`, `check_metrics.py`, `compare_api.py`, `outputs/predictions.jsonl`, `outputs/report.json` и вспомогательные файлы при необходимости.

### Пока не утверждаем

- Финальные `temperature`, `top_p`, `top_k`, `repetition_penalty`, `max_tokens` и `concurrency` — их выбираем по замерам на dev-наборе.
- Точные пороги длинного входа внутри выбранного направления (сколько отзывов оставлять) — направление зафиксировано, пороги подбираются под бюджет токенов.
- Число повторов — предварительно 3 попытки на товар, окончательная цифра по приросту валидности и цене повторов.
- Преимущество API или собственной ВМ.
- Итоговые показатели скорости, качества и цены — их нельзя достоверно заполнить до реальных прогонов.
- Трактовка контракта JSON (ровно пять ключей или дополнительные поля допускаются) — ждём подтверждения.

## 3. Принцип совместной работы

Для каждого существенного решения действуем по циклу:

1. **Обсуждаем вопрос** и фиксируем ограничения.
2. **Формулируем гипотезу**, не объявляя её фактом.
3. **Выбираем небольшой эксперимент**, который различает варианты.
4. **Сохраняем измерения** и проверяем, что они воспроизводимы.
5. **Принимаем решение** и записываем аргументы в журнал ниже.

Не оптимизируем один показатель за счёт нарушения другого. Например, повторная генерация может повысить валидность, но увеличить время и расход токенов.

## 4. Этапы работы

### Этап 0. Уточнить операционные предположения

**Задача:** до реализации договориться о том, как трактуем стоимость и целевую эксплуатацию.

**Решения (согласовано):**

- **ВМ арендуется по требованию.** Включаем её на время пакета и выключаем после. В оплаченное время входит всё: старт инстанса, загрузка модели, прогрев, обработка, запись результатов. Сценарий с постоянно работающей ВМ считаем отдельной строкой сравнения, а не основным.
- **Пакет обрабатывается целиком, отдельными запросами по товарам.** Один запуск `run_batch.py` на `benchmark.jsonl` = 300 строк результата. Месячный объём 50 000 карточек пересчитываем из стоимости одной карточки и добавляем к нему стоимость запусков: `ceil(50000 / 300)` пакетов. Если у заказчика окажется другой размер партии, меняется только число запусков, а не методика.
- **Модель API фиксирована на прогон.** `openai/gpt-oss-20b` без `:free`, дата прогона записывается в отчёт. Переключение модели внутри одного запуска запрещено, иначе сравнение перестаёт быть воспроизводимым.

**Результат этапа:** зафиксированные предположения о графике нагрузки, среде замеров и модели API.

### Этап 1. Проверить данные и сформировать baseline

**Задача:** понять входные данные до настройки модели.

Что проверяем:

- [x] корректность JSONL и уникальность `product_id` — 40 и 300 строк, все ID уникальны;
- [x] реальные поля и возможные пропуски в атрибутах и отзывах — отзывы хранятся строками без рейтингов и дат, минимум 4 отзыва на товар;
- [x] распределение числа отзывов и длины входа в токенах — см. профиль ниже;
- [x] долю товаров, которые не помещаются в 1500 токенов без сокращения — 15% в обоих наборах;
- [ ] время и базовую валидность одной начальной конфигурации на небольшой подвыборке — после запуска сервера.

Вопросы:

- Все ли товары должны получать карточку даже при неполных характеристиках? В наборах нет товаров без отзывов, но отдельные атрибуты могут отсутствовать. Предварительно: карточка нужна для каждого `product_id`, отсутствующие факты не выдумываем и описываем нейтрально.
- Как поступать с `cons`, если во входе нет явных недостатков? `cons` обязателен (1–3 строки), поэтому берём только то, что следует из данных: ограничение из атрибутов или повторяющаяся претензия из отзывов. Если ни того, ни другого нет — одна нейтральная формулировка без вымысла.

#### Профиль данных (измерено 22.10.2026)

Файлы лежат в репозитории. Поля товара: `product_id`, `title`, `category`, `attributes`, `reviews`; `reviews` — список строк без рейтингов и дат. Токены считаны токенайзером `Qwen/Qwen2.5-1.5B-Instruct`.

| Набор | Строк | Уникальных `product_id` | Отзывов на товар | Токенов в отзывах p50 / p90 / max | Товаров > 1500 токенов |
|---|---|---|---|---|---|
| `dev.jsonl` | 40 | 40 | 4–191 | 318 / 2941 / 3687 | 6 (15%) |
| `benchmark.jsonl` | 300 | 300 | 4–220 | 300 / 2779 / 4110 | 45 (15%) |

Числа воспроизводятся командой `python scripts/profile_data.py`.

Что это меняет в плане:

- Категорий 8, `attributes` короткие: p50 63 токена, максимум 75. Основной вклад в длину дают отзывы, а не атрибуты.
- Распределение бимодальное: обычный товар укладывается примерно в 400 токенов, но у 15% товаров 100–220 отзывов и до 4192 токенов товарного содержимого. Проблема не в «среднем товаре», а в отдельном классе длинных карточек, поэтому и решать её нужно точечно, не ухудшая короткие.
- В длинных товарах около 47% отзывов — точные дубликаты. Дедупликация снижает объём отзывов с 3082 до 1722 токенов (медиана), но проблему не решает: даже без system-сообщения и примера карточки в лимит 1500 укладываются только 9 товаров из 45. Значит нужен ещё отбор по бюджету (Этап 4).
- Числа посчитаны только по товарному содержимому, без system-сообщения, примера карточки и chat-template. Реальная доля превышений не меньше 15%, поэтому бюджет считаем по полному собранному запросу.
- Товаров без отзывов в наборах нет (минимум 4), поэтому пустой список отзывов не блокирует контракт карточки.

**Результат этапа:** профиль наборов выше и закрытая измерением задача «сколько товаров не помещается в лимит». Baseline-прогон добавляется сюда же после того, как поднимется сервер (Этап 5), чтобы не оптимизировать параметры вслепую.

### Этап 2. Определить контракт карточки и автоматическую проверку

**Задача:** превратить требования задания в однозначный validator.

Проверяем каждую карточку:

- ответ — один JSON-объект без Markdown и пояснений вокруг;
- есть ровно необходимые поля `product_id`, `description`, `pros`, `cons`, `tags`;
- `product_id` совпадает с входным;
- `description` — строка длиной 120–700 символов и содержит 2–5 предложений;
- `pros` — список из 2–5 непустых строк;
- `cons` — список из 1–3 непустых строк;
- `tags` — список из 3–8 непустых строк.

Сохраняем не только итог `valid/invalid`, но и все причины брака, чтобы одна карточка могла иметь несколько нарушений, если именно так будет устроен отчёт.

Вопросы:

- Считаем ли карточку валидной, если в ней есть дополнительные JSON-поля, или контракт требует ровно пять ключей?
- Как validator должен трактовать повторяющиеся строки в `pros`, `cons` и `tags`: только форматная ошибка или отдельная дополнительная метрика качества?

**Результат этапа:** тестируемая функция валидации и набор граничных тестов для подсчёта предложений, особенно значений вроде `Bluetooth 5.3` и `0.5 л`.

### Этап 3. Разработать промпт и подобрать параметры генерации

**Задача:** добиться приемлемой валидности с минимальными токенами и повторами.

План эксперимента:

1. Собрать system/user prompt из требований карточки, данных товара и примера корректного JSON.
2. Получить baseline на dev-наборе.
3. Перебирать параметры поэтапно, чтобы результаты можно было интерпретировать:
   - `temperature`: 0.0 / 0.3 / 0.7;
   - `top_p`: 0.9 / 1.0;
   - `top_k`: 20 / 50 / без ограничения;
   - `repetition_penalty`: 1.0 / 1.1 / 1.2;
   - `max_tokens`: 250 / 350 / 500.
4. Для каждого запуска фиксировать валидность, причины брака, среднюю длину описания, входные/выходные токены, latency и число попыток.
5. Выбрать параметры по совокупности качества, стоимости и времени, а не только по максимальной валидности.

Вопросы:

- Как строим сетку экспериментов? Решено: сначала меняем по одному параметру, затем проверяем одну комбинацию лучших значений. Полную сетку не гоняем — прогоны стоят времени, а интерпретируемость важнее.

**Политика повторов (принято предварительно, уточняется по замерам):**

- Максимум 3 попытки на товар: 1 основная + до 2 исправляющих. Повтор запускается только при нарушении формата. Смысловое качество текста автоматически не проверяется, поэтому «повтор из-за плохого описания» не предусмотрен.
- В исправляющий запрос добавляем перечень конкретных нарушений от validator; на повторе фиксируем `temperature = 0`, чтобы отличие от основной попытки было только в обратной связи об ошибках.
- В `predictions.jsonl` пишем последнюю попытку с полями `attempts` и `validation_errors`. Если все попытки провалились, строка всё равно сохраняется с `valid: false` и причинами: товар не теряется, метрика считает его браком.
- Долю повторов выводим отдельной метрикой `retry_rate`. Если она выше ~10%, правим промпт, а не увеличиваем число попыток: иначе растут время и стоимость при том же качестве.

**Предварительная гипотеза для проверки:** начать с низкой температуры и короткого, явного контракта, а повтор использовать для исправления конкретно найденных нарушений. Значения параметров окончательно выбираются по замерам.

**Результат этапа:** таблица экспериментов и зафиксированная конфигурация-кандидат.

### Этап 4. Выбрать стратегию длинного входа

**Задача:** не превышать 1500 токенов на карточку и не потерять слишком много полезной информации из отзывов.

Сравниваем варианты:

1. Обрезка отзывов по лимиту.
2. Отбор ограниченного числа отзывов с сохранением разнообразия.
3. Предварительное сжатие отзывов отдельным запросом к модели.

Для каждого оцениваем сложность реализации, входные/выходные токены, дополнительные задержки, валидность JSON и влияние на содержание карточек. Длина должна измеряться токенайзером именно той модели, в том числе для инструкции, примера и chat-template, а не только для списка отзывов.

**Рабочая гипотеза по умолчанию (следует из профиля данных):** дедупликация отзывов → отбор по бюджету токенов с равномерным покрытием списка (начало, конец и середина) → жёсткая проверка полного запроса на ≤ 1500 токенов, при перерасходе обрезаем хвост последнего отзыва. Вариант 3 (сжатие отдельным запросом) не берём в основную ветку: он удваивает число вызовов на 15% товаров, то есть добавляет задержку и стоимость там, где бюджет времени уже самый узкий. Его проверяем только как эксперимент, если качество карточек длинных товаров окажется заметно хуже.

Почему не обрезка «в лоб»: в длинных товарах ~47% отзывов — дубликаты, поэтому обрезка по лимиту потратит бюджет на повторы и потеряет различающиеся мнения.

Вопросы (с предварительными ответами):

- Входит ли 1500 токенов в понимании задания для полного сформированного сообщения или только для товарного содержимого? Берём строгую трактовку — считаем полный собранный запрос вместе с system-сообщением, примером и chat-template. Это сложнее, но проверяемо и не оставляет пространства для спора.
- Важно ли сохранять все отзывы? Нет. Полный список у 15% товаров физически не помещается в лимит, а отбор покрывает начало, конец и середину списка, поэтому разные мнения сохраняются.
- Допустим ли дополнительный вызов модели для сжатия? Только как отдельный эксперимент, в основную ветку не идёт: он удваивает число вызовов и задержку именно на самых тяжёлых товарах.

**Результат этапа:** реализованная стратегия, тест на самых длинных входах и статистика до/после сокращения.

### Этап 5. Замерить batching и выбрать concurrency

**Задача:** обработать 300 товаров не дольше 480 секунд на одной T4, а по цене — не дольше 415 секунд (см. п. 1.2).

**Среда замеров.** Локальная GPU: NVIDIA GeForce RTX 2060, 6 ГБ, драйвер 610.62, PyTorch 2.5.1+cu124. vLLM в текущем окружении не установлен; официально он поддерживается на Linux, поэтому сервер поднимаем в WSL2 (или в контейнере), а не через нативный Windows-Python. Способ запуска меняется, методика измерения — нет.

**Ограничения железа, которые влияют на конфигурацию:**

- 6 ГБ памяти: `Qwen2.5-1.5B-Instruct` в fp16 занимает около 3.1 ГБ весов, остальное уходит на KV-cache и активации. `--max-model-len 4096` и `--gpu-memory-utilization 0.9` берём из задания, но при OOM первым уменьшаем `--max-model-len`, а не точность и не длину промпта.
- Turing не поддерживает bfloat16, поэтому `--dtype half` — единственный корректный вариант, и он же указан в задании.
- У T4 16 ГБ памяти, у нашей карты 6 ГБ, поэтому предел одновременно обрабатываемых последовательностей ниже и падение throughput на высоком `concurrency` ожидаемо раньше. Прямого замера на T4 нет: SLA проверяем пересчётом из измеренного throughput и в отчёте помечаем результат как оценку, а не как прогон на T4.
- `--enforce-eager` отключает CUDA graphs и стоит части скорости. Оставляем его для стабильности на 6 ГБ и проверяем разницу отдельным коротким замером, если останется запас по времени.

План:

1. Поднять vLLM с конфигурацией из задания и проверить доступность OpenAI-совместимого endpoint.
2. Проверить одиночный запрос и корректность измерения времени.
3. Прогнать один и тот же тестовый набор с `concurrency = 1, 4, 16, 32` (при необходимости расширить диапазон). На 6 ГБ часть точек может упасть в OOM — это фиксируем как результат замера с указанием причины, а не скрываем.
4. Собирать общую длительность, throughput (карточек/сек), среднюю latency завершённого запроса, желательно p95, процент валидных ответов, число повторов, ошибки и расход токенов.
5. Выбрать точку, в которой throughput достаточно высок, но не падает качество и не растёт чрезмерно latency.
6. Запустить полный benchmark на выбранной точке и сохранить результаты.

**Методика измерения (зафиксирована):**

- `elapsed_sec` — от начала обработки пакета (после загрузки модели) до записи последней строки. Старт сервера и загрузку модели меряем отдельно и показываем в стоимости отдельной строкой.
- `latency` карточки — wall-clock от постановки задачи в клиенте до получения ответа, включая ожидание в семафоре. Дополнительно сохраняем `request_sec` — чистое время HTTP-запроса, чтобы отделить эффект очереди от скорости модели.
- Публикуем среднее и p95: требование задания сформулировано про среднее время, но хвост важен для эксплуатации. Способ измерения между запусками не меняем.
- Ошибка одного запроса не перезапускает пакет: повторяем только эту карточку, успешные результаты сохраняются. Исключение — падение сервера: тогда прогон повторяем целиком и отмечаем это в отчёте.

**Результат этапа:** таблица `concurrency → throughput / latency / valid_rate`, полный `predictions.jsonl` и сырые метрики запуска.

### Этап 6. Сравнить с внешним API

**Задача:** сравнить локальный сервис и API на одной задаче и сопоставимой выборке.

План:

1. Использовать тот же промпт и тот же код сборки входа, что и для локального сервера.
2. Зафиксировать OpenRouter как единственного API-провайдера: `OPENROUTER_API_KEY`, base URL `https://openrouter.ai/api/v1`, модель `openai/gpt-oss-20b` (платный эндпоинт, без `:free`). Прямой OpenAI и `OPENAI_API_KEY` в этом спринте не используем. Записать модель, base URL и дату прогона в `outputs/report.json` (`api_comparison.model`, `api_comparison.base_url`, `api_comparison.api_run_date`).
3. Обработать 30 товаров из `benchmark.jsonl`, чтобы получить прямое попарное сравнение с локальным прогоном: 10 самых длинных по токенам плюс 20 остальных, взятых с равным шагом по списку. Подвыборка детерминирована и воспроизводится повторно.
4. Сохранить фактические `usage.prompt_tokens` и `usage.completion_tokens` от API, не подставляя локальный токенайзер.
5. Ограниченные повторы: `429` и `5xx` — экспоненциальная задержка (2 с, множитель 2, не более 5 попыток, потолок 30 с). `400`, `401`, `403` не повторяем: это ошибка запроса или ключа, её нужно исправлять, а не ждать. Обрыв соединения считаем временной ошибкой с тем же лимитом попыток.
6. Повторы из-за невалидного формата считаем отдельно от сетевых: сравнение ведём и по базовой генерации, и по полному рабочему процессу с разрешёнными 3 попытками, чтобы цена повторов была видна явно.

Вопросы:

- Достаточно ли 30 товаров для сравнения или нужно увеличить выборку до 100, если стоимость прогона через API это позволяет? Решение принимаем после оценки цены одной карточки на этом этапе.

**Результат этапа:** `api_comparison` в `outputs/report.json`, сырые ответы API в `outputs/api_predictions.jsonl` и сравнительная таблица в README.

### Этап 7. Рассчитать стоимость и точку выбора API/ВМ

**Задача:** подкрепить рекомендацию арифметикой из реальных измерений.

Формулы по условным тарифам задания:

- ВМ: `cost_vllm_per_1000 = (elapsed_sec / 3600 * 65) / n * 1000`.
- API: `cost_api_per_1000 = (input_tokens * 20 + output_tokens * 60) / 1_000_000 / n * 1000`, но только если OpenRouter вернул ненулевой фактический `usage` по успешным запросам. Если `usage` отсутствует из-за `request_error`, `403`, сетевой блокировки или другого отказа до модели, `outputs/report.json` должен содержать `costs.api = null`, а не `0.0`, чтобы машинный отчёт не трактовал недоступный API как бесплатный.

Повторные вызовы учитываем и во времени, и в токенах. Для API используем usage именно API-модели, а не локальный токенайзер.

Отдельно строим сценарии месячного объёма и явно описываем, включено ли время простоя ВМ в расходы. Не смешиваем переменную цену активного часа с фиксированной ежемесячной платой за постоянно работающую ВМ.

Вопросы:

- Есть ли дополнительные расходы, которые требуется включить помимо ставок из задания? По условию курса сначала считаем по заданным тарифам, дополнительные допущения выделяем отдельно.

Режим аренды уже зафиксирован на Этапе 0 (по требованию), поэтому основной расчёт строим для него, а вариант 24×7 показываем как отдельную строку для сравнения.

**Результат этапа:** сравнение при 50 000 карточек в месяц, точка безубыточности при зафиксированных предположениях и краткая рекомендация.
