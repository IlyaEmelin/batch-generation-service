## 2. Краткое описание системы

`batch-generation-service` — пакетный генератор карточек товаров для
маркетплейса на русском языке. На вход подаётся JSONL-файл, где одна строка —
один товар с атрибутами и отзывами покупателей. Для каждого товара сервис:

1. собирает chat-запрос в бюджет **1500 токенов** (считается по полному
   chat-template, включая system-сообщение и пример карточки);
2. отправляет запрос в локальный vLLM по OpenAI-совместимому
   `/v1/chat/completions`;
3. проверяет ответ по структурному контракту из пяти ключей;
4. при нарушении формата делает исправляющую попытку с перечнем конкретных
   нарушений (до трёх попыток на товар);
5. пишет результат в `outputs/predictions.jsonl` **в порядке входа** и сводку
   запуска в JSON.

Модель — `Qwen/Qwen2.5-1.5B-Instruct` (float16, vLLM 0.31.0 в WSL2). Дополнительно
реализованы пересчёт отчёта из сохранённых артефактов (`check_metrics.py`),
сравнение с внешней моделью на том же промпте и валидаторе (`compare_api.py`) и
подбор параметров генерации (`tune_params.py`).

## 4. Не входит в текущую версию

- REST/gRPC-сервис поверх пакетного pipeline: сейчас это CLI-скрипты.
- Очередь задач, база данных, долговременное хранение и ретраи на уровне
  платформы.
- Автоматический fallback на внешний API для карточек, не прошедших контракт.
- Ручная модерация, UI или очередь на исправление невалидных карточек: сервис
  только помечает их `valid=false` и заполняет `validation_errors`.
- Production-мониторинг, алерты, SLA-dashboard, метрики Prometheus.
- Фактический benchmark на NVIDIA T4: все замеры скорости и стоимости сделаны
  на локальной RTX 2060.
- Гарантированное достижение цели 25 ₽ / 1000 карточек на T4: локальный RTX 2060 замер уложился, но T4 не проверялась.
- Семантическая проверка качества текста: проверяется только структура и
  формальные ограничения, «фактичность» и отсутствие выдумок не валидируются.
- Проверка отсутствия `#` в тегах: это требование есть в промпте, но
  валидатором не проверяется.
- Дедупликация смысловых повторов внутри `pros` / `cons` / `tags`.
- Мультиязычность: промпт и контракт рассчитаны на русский язык.
- Батч-инференс средствами vLLM: используется обычный chat-completions с
  клиентским `ThreadPoolExecutor`.

## 5. Пользователи и сценарии

| Роль | Сценарий | Интерфейс |
|---|---|---|
| Разработчик/оператор | прогнать партию товаров на локальной модели | `run_batch.py` |
| Разработчик | пересчитать отчёт и стоимость из артефактов | `check_metrics.py` |
| Разработчик | сравнить локальную модель с внешней на одинаковом входе | `compare_api.py` |
| Разработчик | подобрать параметры генерации на подвыборке | `tune_params.py` |
| Ревьюер | проверить результат без запуска модели | `outputs/predictions.jsonl`, `outputs/report.json` |

Основной сценарий (`FR-01 … FR-10`):

```text
benchmark.jsonl
  -> load_rows
  -> prepare_prompt (дедупликация, отбор отзывов, бюджет 1500)
  -> vLLM /v1/chat/completions (concurrency 16)
  -> validate_card
      ├─ valid   -> строка результата
      └─ invalid -> corrective_message (до 3 попыток)
  -> outputs/predictions.jsonl (в порядке входа)
  -> outputs/predictions.summary.json (сводка запуска)
```

Отчёт (`FR-11`):

```text
outputs/predictions.jsonl + predictions.summary.json
  + outputs/sweep_*.summary.json + outputs/api_summary.json
  + outputs/parameter_experiments.csv
  -> check_metrics.py
  -> outputs/report.json
```

## 6. Входные данные

Формат: JSONL, UTF-8, одна строка — один товар, пустые строки пропускаются.
Файлы в репозитории: `benchmark.jsonl` (300 товаров, основной прогон) и
`dev.jsonl` (подвыборка для подбора параметров).

| Поле | Тип | Обязательность | Использование |
|---|---|---|---|
| `product_id` | `str` | обязательно | ключ результата, проверяется на точное совпадение |
| `title` | `str` | обязательно | строка «Название» в промпте |
| `category` | `str` | опционально | строка «Категория», добавляется только если непустая |
| `attributes` | `dict[str, str]` | обязательно | переводится в строку «Атрибуты: имя: значение, …» |
| `reviews` | `list[str]` | обязательно | источник отзывов; дедуплицируется и урезается по бюджету |

Пример реальной записи (сокращён):

```json
{
  "product_id": "P-1144",
  "title": "Увлажнитель воздуха Freso Soft",
  "category": "Бытовая техника / Увлажнители воздуха",
  "attributes": {"бренд": "Freso", "тип": "ультразвуковой", "объём бака": "2 л"},
  "reviews": ["В целом Пар мягкий, мебель вокруг не мокнет", "..."]
}
```

Ограничения входа, принимаемые как данность:

- `product_id` считается уникальным в пределах файла: проверки на дубли во
  входе нет, дубли считаются уже в результате (`duplicate_product_ids`).
- Если служебная часть промпта без отзывов не влезает в лимит, `prepare_prompt`
  выбрасывает `ValueError` и партия падает: это нарушение предусловия, а не
  штатная ошибка строки.
- Схема входа не валидируется отдельно: отсутствие обязательного поля проявится
  как `KeyError` при сборке промпта.

## 7. Выходные данные и артефакты

### 7.1. `outputs/predictions.jsonl`

Одна строка на каждый `product_id`, строго в порядке входа. Карточка лежит в
верхнем уровне строки, а не во вложенном объекте.

| Поле | Тип | Смысл |
|---|---|---|
| `product_id` | `str` | идентификатор товара |
| `valid` | `bool` | прошла ли карточка контракт после всех попыток |
| `attempts` | `int` | число выполненных попыток (1–3) |
| `validation_errors` | `list[str]` | нарушения контракта в **последней** попытке |
| `attempt_errors` | `list[str]` | накопленные нарушения по всем неудачным попыткам |
| `input_tokens` | `int` | входные токены последнего запроса |
| `output_tokens` | `int` | выходные токены последнего запроса |
| `total_input_tokens` | `int` | сумма входных токенов по всем попыткам |
| `total_output_tokens` | `int` | сумма выходных токенов по всем попыткам |
| `planned_input_tokens` | `int` | максимум расчётной длины запроса по попыткам |
| `latency_sec` | `float` | время от постановки в очередь до результата (включая ожидание) |
| `request_sec` | `float` | время последнего HTTP-запроса |
| `reviews_total` | `int` | отзывов во входе |
| `reviews_used` | `int` | отзывов попало в промпт |
| `truncated` | `bool` | отзывы урезаны (часть отброшена или последний обрезан) |
| `description` | `str \| null` | поле карточки, `null` при провале |
| `pros` | `list[str] \| null` | поле карточки |
| `cons` | `list[str] \| null` | поле карточки |
| `tags` | `list[str] \| null` | поле карточки |
| `raw_response` | `str` | сырой ответ последней попытки |
| `error` | `str \| null` | текст сетевой/серверной ошибки, если была |

Важно: при `valid=false` строка **не удаляется** и не заменяется шаблоном —
она остаётся в файле с `validation_errors`, чтобы брак был виден и считался.

### 7.2. Сводка запуска

`run_batch.py` пишет JSON рядом с `--output`: по умолчанию
`outputs/predictions.summary.json` (путь можно задать через `--summary`).
Содержит: `input_file`, `rows`, `started_at`, `elapsed_sec`,
`throughput_cards_per_sec`, `concurrency`, `params`, `server`
(`base_url`, `vllm_version`), `environment` (Python, платформа, GPU, версии
`torch`/`transformers`/`openai`), `valid_rate`, `retry_rate`,
`errors_by_reason`, `retry_errors_by_reason`, `latency_mean_sec`,
`latency_p95_sec`, `request_mean_sec`, `request_p95_sec`,
`total_input_tokens`, `total_output_tokens`, `max_planned_input_tokens`,
`max_input_tokens`, `truncated_rows`.

### 7.3. `outputs/report.json`

Собирается `check_metrics.py` и состоит из блоков:

| Ключ | Содержимое |
|---|---|
| `generated_at` | время сборки отчёта |
| `run` | сводка основного прогона (из `predictions.summary.json`) |
| `server` | `startup_sec`, версия vLLM, пояснение методики |
| `metrics` | метрики, пересчитанные из `predictions.jsonl` |
| `concurrency` | таблица прогонов `1 / 4 / 16 / 32` |
| `costs` | тариф, цель, стоимость vLLM, стоимость API, режим 24×7 |
| `tuning` | результаты `parameter_experiments.csv` (10 конфигов) |
| `format_postprocessing` | доля ответов с Markdown-обёртками отдельно для локального прогона и API |
| `api_comparison` | сводка `api_summary.json` + `local_same_subset` (локальные метрики на тех же 150 товарах) |
| `sla` | цель 480 с и фактическое/оценочное время на 300 карточек |

### 7.4. Финальные артефакты сдачи

В git отслеживаются только эти файлы из `outputs/`:

outputs/report.json

## 8. Контракт карточки товара

### 8.1. Целевой JSON

```json
{
  "product_id": "P-1144",
  "description": "Ультразвуковой увлажнитель Freso Soft с баком на 2 литра. Работает тихо и рассчитан на комнату до 20 м². Автоотключение есть, подсветки нет.",
  "pros": ["Тихая работа", "Автоотключение при пустом баке"],
  "cons": ["Бака на 2 л хватает на одну ночь"],
  "tags": ["увлажнитель", "для дома", "детская"]
}
```

Ровно пять ключей в указанном порядке, без Markdown и пояснений вокруг JSON.

### 8.2. Правила и их проверка

| Поле | Правило | Код ошибки |
|---|---|---|
| весь ответ | парсится как JSON | `not_json` |
| весь ответ | JSON-объект, а не массив/строка | `not_object` |
| набор ключей | присутствуют все пять | `missing_keys` |
| набор ключей | нет лишних ключей | `extra_keys` |
| `product_id` | строка, точно равна входному | `product_id_mismatch` |
| `description` | строка | `description_not_string` |
| `description` | 120–700 символов | `description_length` |
| `description` | 2–5 предложений | `description_sentences` |
| `pros` | список | `pros_not_list` |
| `pros` | 2–5 элементов | `pros_count` |
| `pros` | все элементы — непустые строки | `pros_item` |
| `cons` | список | `cons_not_list` |
| `cons` | 1–3 элемента (пустой запрещён) | `cons_count` |
| `cons` | все элементы — непустые строки | `cons_item` |
| `tags` | список | `tags_not_list` |
| `tags` | 3–8 элементов | `tags_count` |
| `tags` | все элементы — непустые строки | `tags_item` |
| `description`, `pros`, `cons`, `tags` | нет китайских, японских и корейских символов | `contains_cjk_chars` |
| запрос | сеть/сервер не вернули ответ | `request_error` |

Правила подсчёта:

- Предложения считаются регуляркой `(?<=[.!?…])\s+`: разделитель требует
  пробела после знака, поэтому «Bluetooth 5.3» и «0.5 л» остаются одним
  предложением.
- Валидатор возвращает **все** нарушения, а не первое: одна карточка может
  дать несколько кодов одновременно.
- Markdown-ограждения (тройные обратные кавычки с меткой `json`) перед разбором
  снимаются и ошибкой не считаются — это компенсация поведения модели, а не
  часть контракта.
- Повторяющиеся строки внутри `pros` / `cons` / `tags` ошибкой не считаются:
  это вопрос качества текста, а не структуры.
- CJK-проверка ищет диапазоны иероглифов, каны и хангыля
  (`\u3040-\u30ff`, `\u3400-\u4dbf`, `\u4e00-\u9fff`, `\uf900-\ufaff`,
  `\uac00-\ud7af`). На карточку пишется **одна** ошибка `contains_cjk_chars`,
  даже если символы нашлись в нескольких полях: иначе счётчик причин брака
  раздувается. Подсказка для исправляющей попытки просит переписать текст
  по-русски.

### 8.3. Что контрактом не проверяется

| Требование из промпта | Проверяется валидатором |
|---|---|
| «только факты из данных», без выдумок | нет |
| отсутствие `#` в тегах | нет |
| отсутствие смысловых дублей в списках | нет |
| уместность и связность текста | нет |
| число предложений ровно три (в промпте — рекомендация) | нет, проверяется диапазон 2–5 |

Следствие: `valid=true` означает «структурно корректная карточка», а не
«хорошая карточка». Смысловое качество в текущей версии оценивается только
глазами на сэмпле.

## 9. Архитектура и поток данных

```text
Windows (клиент, Python 3.11.9)
┌──────────────────────────────────────────────────────────────┐
│ run_batch.py                                                 │
│   load_rows -> prepare_prompt -> ThreadPoolExecutor(16)      │
│        -> OpenAI client (httpx, timeout 120/connect 10)      │
│        -> validate_card -> corrective_message (retry)        │
│   -> predictions.jsonl + predictions.summary.json            │
│                                                              │
│ check_metrics.py  -> report.json                             │
│ compare_api.py    -> api_predictions.jsonl + api_summary.json│
│ tune_params.py    -> parameter_experiments.csv               │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTP 127.0.0.1:8000/v1
┌───────────────────────────▼──────────────────────────────────┐

└──────────────────────────────────────────────────────────────┘
```

Разделение ответственности:

| Модуль | Ответственность | Не знает про |
|---|---|---|
| `cardgen.py` | вход, сборка промпта, бюджет токенов, валидатор, corrective hints | HTTP, модель, файлы результата |
| `run_batch.py` | оркестрация партии, retries, запись результата и сводки | расчёт отчёта |
| `check_metrics.py` | метрики, стоимость, сборка `report.json` | модель и генерацию |
| `compare_api.py` | сравнение с внешним провайдером на том же ядре | локальный сервер |
| `tune_params.py` | перебор параметров на подвыборке | продакшн-настройки |

Ключевое архитектурное решение: `cardgen.py` общий для `run_batch.py`,
`compare_api.py` и `tune_params.py`. Поэтому различия в результатах локальной и
внешней модели относятся к модели, а не к промпту или правилам приёмки.

Порядок результатов обеспечивается не порядком завершения задач, а индексами:
`results[index] = result` в `__generate_cards_concurrently`, запись — после
`as_completed` по всему списку.

## 10. Подготовка промпта и бюджет 1500 токенов

Бюджет считается по **полному собранному запросу**: system-сообщение, пример
карточки, данные товара, отзывы и chat-template. Это строгая трактовка
ограничения: если считать только отзывы, фактический вход превысит лимит.

Константы (`cardgen.py`, `run_batch.py`):

| Константа | Значение | Смысл |
|---|---|---|
| `DEFAULT_LIMIT` | 1500 | лимит токенов полного запроса |
| `RETRY_RESERVE` | 150 | резерв под исправляющий запрос, применяется только при `max_attempts > 1` |
| `DEFAULT_MODEL` | `Qwen/Qwen2.5-1.5B-Instruct` | модель и токенизатор по умолчанию |
| `--max-tokens` | 350 | бюджет ответа |
| `--max-model-len` (vLLM) | 4096 | вход + ответ + запас |

Алгоритм `prepare_prompt(row, tokenizer, limit)`:

1. Собираются сообщения без отзывов и считается их длина: `count_chat_tokens`
   вызывает `apply_chat_template(..., add_generation_prompt=True,
   return_dict=True)` и требует dict-like результат с `input_ids`. Если формат
   отличается, скрипт падает с явной ошибкой, чтобы не посчитать `len()` от
   контейнера вместо реального числа токенов.
2. Если служебная часть уже больше `limit` — `ValueError`, товар не обработать.
3. Отзывы дедуплицируются точным сравнением строк.
4. Стоимость отзыва = токены текста + токены разделителя `"\n- "`.
5. Отзывы перебираются в порядке `__spread_order`: 0, последний, 1,
   предпоследний, … и добавляются, пока влезают в остаток бюджета.
6. Выбранные индексы сортируются по возрастанию, чтобы порядок в промпте
   совпадал с исходным.
7. Длина пересчитывается по собранному запросу целиком. Пока превышает лимит,
   отзывы удаляются с конца; если остался один и он не влезает — он обрезается
   бинарным поиском по символам.
8. Возвращаются сообщения и статистика: `input_tokens`, `reviews_total`,
   `reviews_used`, `truncated`.

При `--max-attempts 3` (значение по умолчанию) в `prepare_prompt` передаётся
`limit = 1500 − 150 = 1350`, чтобы исправляющее сообщение с перечнем нарушений
тоже уложилось в 1500.

Фактическое состояние:

| Метрика | Значение |
|---|---|
| `max_planned_input_tokens` | 1399 (пересчёт по всем попыткам, включая исправляющие) |
| `max_input_tokens` | 1399 (по usage провайдера) |
| `rows_over_input_limit` | 0 |
| `truncated_rows` | 45 из 300 — у них отброшена часть отзывов |

## 11. Генерация, повторы и обработка ошибок

Партия обрабатывается `ThreadPoolExecutor(max_workers=args.concurrency)`.
Значение по умолчанию — 16: на sweep-замерах это точка насыщения, на 32
throughput падает, а latency запроса растёт.

Одна карточка (`generate_card`):

```text
prepared = prepare_prompt(row, tokenizer, limit - reserve)
for attempt in 1..max_attempts:
    planned = count_chat_tokens(messages)
    if planned > limit: raise ValueError          # fail-fast, роняет партию
    response = chat.completions.create(...)
        on exception: error=<текст>, validation_errors=[request_error], return
    accumulate tokens, attempts, request_sec, raw_response
    checked = validate_card(raw, product_id)
    if checked.valid: return result
    attempt_errors += checked.errors
    messages = prepared.messages + [corrective_message(checked.errors, id)]
```

Правила и следствия:

| Правило | Реализация | Следствие |
|---|---|---|
| Первая попытка использует `--temperature` | `temperature if attempt == 1 else 0.0` | при дефолте `0.0` все попытки детерминированы |
| Повторы только по формату | смысловых проверок нет | сервис не «улучшает» валидную, но слабую карточку |
| Исправляющее сообщение — человекочитаемое | `__ERROR_HINTS` переводит коды в требования на русском | модели 1.5B бесполезно показывать `cons_count` |
| Каждый повтор идёт от исходных сообщений | `prepared.messages + [corrective]` | предыдущие исправления не накапливаются, промпт не растёт |
| `product_id` повторяется в конце пользовательского сообщения | `__build_messages` | на длинном входе модель не теряет id |
| `top_k` передаётся только при `> 0` | `extra_body` | `0` означает «не передавать» |
| `repetition_penalty` передаётся только при `≠ 1.0` | `extra_body` | дефолт не засоряет запрос |
| `response_format={"type": "json_object"}` | флаг `--json-response-format`, по умолчанию выключен | vLLM 0.31.0 отдаёт голый JSON без Markdown-обёрток; снятие ограждений остаётся как fallback |
| `run_batch` не повторяет сетевые ошибки | `except Exception` → `request_error` | строка фиксируется как брак, партия продолжается |
| `compare_api` повторяет сетевые ошибки | до 5 попыток; повторяются только `429` и `5xx`; задержка = `Retry-After`, иначе экспонента 2…30 с, плюс jitter до 25 %, но не больше 60 с | нестабильность сети не выглядит как цена модели, одновременные клиенты не бьются в лимит синхронно |

Таймаут клиента в `run_batch`: `httpx.Timeout(120.0, connect=10.0)`,
`max_retries=0`. В `compare_api` — `httpx.Timeout(180.0, connect=15.0)`, повторы
реализованы вручную, поэтому `max_retries=0` у клиента, чтобы не удваивать попытки.

`latency_sec` включает ожидание в очереди пула: это время от постановки задачи
до получения результата. `request_sec` — только последний HTTP-запрос. Поэтому
`latency_mean_sec` (161.8 с) и `request_mean_sec` (11.3 с) отличаются на порядок
и измеряют разные вещи.

Тариф — 65 ₽ за час работы ВМ по требованию, то есть оплачивается только время партии. Источник чисел — `costs` в `outputs/report.json`.

Выводы по экономике, зафиксированные в текущей версии:

- При наличии ВМ локальный вариант дешевле API: фактический локальный прогон стоит 19.68 ₽/1000, API-подвыборка на 150 строках — 37.958 ₽/1000. Партия на 300 карточек стоит около 5.90 ₽ локально против 11.39 ₽ через API при тех же тарифах.

- Главный резерв локального варианта — снижение `retry_rate` с 0.360: каждая повторная попытка — это ещё один полный вход ~1300 токенов, а основные причины повторов — CJK и число предложений (120 из 174 случаев).

un_batch.py,
поэтому полный прогон и инструкция запуска используют одно и то же.

## 19. Ограничения, риски и известные расхождения

### 19.1. Пересборка отчёта из сдачи

`outputs/predictions.summary.json` и `outputs/sweep_*.summary.json` не входят в
git (см. п. 7.4). Раньше из-за этого `python check_metrics.py --startup-sec 204`
на свежем клоне падал с `SystemExit`, а таблица `concurrency` оставалась пустой.
Теперь `check_metrics.py` при отсутствии файла берёт соответствующий блок из
предыдущего `report.json` и печатает предупреждение:

| Чего нет | Откуда берётся |
|---|---|
| `predictions.summary.json` | `report.json → run` |
| `sweep_*.summary.json` | `report.json → concurrency` |
| `api_summary.json` | `report.json → api_comparison` |
| `parameter_experiments.csv` | `report.json → tuning` |

Ограничения остаются два:

- `outputs/predictions.jsonl` обязателен: все метрики качества считаются из него;
- fallback восстанавливает **параметры прошлого прогона**. После новой генерации
  нужно передать `--summary`, иначе блок `run` в отчёте останется старым.
  Это осознанный компромисс: лучше пересобрать отчёт с предупреждением, чем
  упасть на чистом клоне.

### 19.2. Ограничения методики и замеров

| Ограничение | Влияние | Как проверено |
|---|---|---|
| T4 не измерялась | SLA 480 с подтверждён только на локальной GPU (326.99 с) | доступа к T4 нет |
| Разные режимы concurrency | 19.68 ₽/1000 на полном прогоне при 16; sweep 32 даёт оценку ≈16.70 ₽/1000, но не подтверждён полным прогоном | `outputs/report.json` |
| API-сравнение на 150 товарах | всё ещё подвыборка, а не полный benchmark | `rows=150` в `api_comparison` |
| Локальная подвыборка тех же 150 товаров | 0.920 против 0.937 на всех 300 — подвыборка чуть сложнее полного набора | `local_same_subset` |
| Валидация структурная | `valid=true` не гарантирует смысл | в валидаторе нет семантики |
| CJK-вставки Qwen | 8 карточек из 300 не исправились за три попытки | `contains_cjk_chars` |
| `#` в тегах не проверяется | требование промпта не обеспечено | см. п. 8.3 |
| Нет проверки входа | битый JSONL даёт `KeyError`/`ValueError` на всю партию | `load_rows` без схемы |

| Треть карточек требует повтора | удвоение стоимости и времени на этих строках | `retry_rate=0.3600` |
| Один сервер, одна GPU | нет горизонтального масштабирования | архитектура CLI |
| Нет fallback/очереди/мониторинга | не production-ready | вне области версии |

### 19.3. Риски при повторных прогонах

- **Другая версия vLLM или модели** изменит `valid_rate`; версия сервера
  фиксируется в сводке, но не пинуется в коде.
- **Другой драйвер/температура GPU** изменит только скорость и стоимость,
  качество останется в пределах, наблюдаемых сейчас.
- **Запуск `compare_api.py` без `--reasoning-effort low --max-tokens 500`**
  даст несопоставимые цифры (см. п. 17).
- **Запуск без `--json-response-format`** вернёт Markdown-обёртки: валидатор их
  снимет, но `format_postprocessing` покажет ненулевой `markdown_fenced_rate`,
  а расход выходных токенов вырастет.
- **Изменение `--max-attempts`** меняет `limit` для отбора отзывов
  (1500 − 150), поэтому сравнение прогонов с разным числом попыток некорректно
  по длине входа.
- **Разные версии transformers у клиента** раньше давали разный `planned`
  (`BatchEncoding` против списка). Сейчас код явно запрашивает `return_dict=True`
  и проверяет наличие `input_ids`; при обновлении библиотеки стоит перепроверить
  `max_planned_input_tokens`.

## 21. Открытые вопросы и бэклог

Вопросы, которые нужно решить до следующей версии:

1. **Что считать качеством карточки помимо структуры.** Сейчас 0.937 — это
   доля структурно валидных. Нужна ли оценка смысла (ручная разметка или
   LLM-judge) и какой порог считать приёмкой.
2. **Допустимый уровень брака.** 19 карточек из 300 уходят в ручную модерацию,
   из них 8 — из-за CJK-вставок. Если это дорого, нужен либо fallback на
   внешнюю модель, либо escalate-очередь.
3. **Целевой объём и цена.** 50 000 карточек в месяц при 19.68 ₽/1000 — это
   ~984 ₽; при какой цене проект считается выгодным и нужен ли T4-замер до
   решения.
4. **Нужно ли снижать `retry_rate`.** Основные причины — число предложений (65)
   и CJK (55); правка промпта, постфильтр или few-shot могут дать больше, чем
   подбор параметров.

Бэклог (не входит в текущую версию):

- постфильтр CJK или constrained decoding, чтобы убрать 8 остаточных карточек;
- добавить валидацию `#` в тегах и минимальную проверку смысловых дублей;
- семантическая проверка описания (факты из атрибутов, отсутствие выдумок);
- измерить на T4 и подтвердить SLA;
- снизить `retry_rate` через правку промпта и повторный tuning на большей
  подвыборке (не 40, а ≥150 товаров);
- рассмотреть offline batch inference vLLM вместо chat-completions;
- fallback на внешний API для карточек, не прошедших контракт после трёх попыток.

## 22. Сводка

Сервис решает задачу пакетной генерации карточек и доводит её до проверяемого
результата: 300 из 300 строк, 281 валидная карточка (0.9367), 0 строк сверх
лимита 1500 токенов, 0 дублей, порядок сохранён, все числа воспроизводимы по
артефактам.

Что подтверждено фактами: контракт и бюджет токенов, устойчивость к формату,
